From "send me a screenshot" to seeing it yourself

Most support questions are about what one person sees. Logging in as them is the fastest way to answer, as long as it is controlled.

Before

  • Long back-and-forth with screenshots
  • Shared passwords or temporary password resets
  • No record of who looked at which account
  • Changes made "as the user" with no trace of the real person

After

  • No password is shared, changed or reset
  • Every session logged with reason, IP, browser and duration
  • Changes recorded field by field, messages signed by the real user

Safe by design

Every rule is checked on the server, on each request, not only by hiding buttons.

  • Only members of the Log in as other users group can start a session; the group is empty when the app is installed
  • Calls made outside your own web browser session (external API scripts) cannot start a session
  • The browser session is switched the same way a normal login does it, with a new session id, so the user's own access rights, record rules, companies and language apply
  • Return gives back your own session; if your account changed in the meantime (password, login, archived) you are logged out instead
  • Passwords, security keys and consent settings of the user can never be changed from an impersonated session
  • Time limit, idle timeout and sessions ended by a manager are enforced by the server on the next request
  • Messages posted while impersonating are signed with your name, never the user's
  • Only a hash of the browser session id is stored, never the session id itself

Questions

Who can log in as other users after installing?

Nobody. Add the Log in as other users right to the people who need it, in Settings, Users. Optionally create policies to narrow who may log in as whom.

Can I log in as an administrator?

Not by default. With the Administrators setting on, system administrators may log in as other administrators, and only if they have the same rights or more. The superuser can never be impersonated.

Does the user's password change?

No. No password, security key or two-factor setting is read, reset or changed. The switch works like a login on your own browser session.

What happens when the time is up?

On the next click the server ends the session and gives your own account back. The banner counts down and returns you automatically, and a scheduled job closes sessions whose browser was closed.

What exactly does read-only block?

Creating, changing and deleting records, saving filters and posting messages, including changes the portal or website would make on the user's behalf. Opening screens, searching and printing still work.

Are my changes attributed to the user?

Record changes are stored in the activity log under your session with the old and new values. Messages and notes are signed with your name.

Can I log in as portal customers?

Yes. You land on their portal pages with the same banner and Return button. Portal users can never start a session themselves.

Does it work with several companies?

Yes. You can only log in as users whose companies are all among yours, and managers only see the sessions of their companies. Policies can be limited to companies.

Can I start a session from an API script?

No. Sessions can only be started from your own browser session, so the banner, the time limit and the return always apply.

How long are logs kept?

365 days by default. Change the retention in Settings, or set 0 to keep them forever.
